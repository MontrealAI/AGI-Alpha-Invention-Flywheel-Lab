# MONTREAL.AI public invention pilot

The immediate recipient is the MONTREAL.AI operator who has to construct reliable decision tools whenever a new evidence contract arrives. The costly step is constructing and qualifying bespoke logic. Test an inventor that can select which development examples it needs to write and repair that logic. Established deterministic SQL remains the operating alternative once a contract is stable.

## Inputs and autonomy boundary

Start from the public My Frontier release at `162ac807c6a7302fa8b4fd6fa1a03ff786fd1f41`. The operator supplies objectives, schemas, authority, a finite resource allocation and the evaluation rules. Three opportunities use the public member edition data, the seven published Endpoint Screen observations or a dependency projection of the released Foundry files. None of the builder prompts carries the solution query, reference program, confirmation rows or confirmation output. The opportunity model sees only summaries of the three open problems. Each subsequent construction starts a separate stateless session. The held confirmation cases are a shared-host boundary with independently written Python references. This is public experimental data under one operator.

The winner of the model's first opportunity selection becomes the A₁ mission. If choice abstains, end the causal comparison. Attempt construction and repairs on development feedback within the token allocation. If it emits an artifact, run the separate evaluator. An artifact can seed exploratory method learning after a failed first qualification, with that outcome preserved. Ask the model to derive a reusable case-ordering policy from its experience. The only provided capability is a read-only SQL interface over development case descriptions and observed failures. The model chooses the policy.

## Measurement

- Qwen3-8B Q4_K_M at Hugging Face revision `7c41481f57cb95916b40956ab2f0b139b296d974`. SHA-256 `d98cdcbd03e17ce47681435b5150e34c1417f50b5c0019dd560e4882c5745785`.
- llama.cpp b12242 on Linux CPU, four threads, one slot, 8192 context tokens, no prompt caching, temperature zero, seed 713 and reasoning mode off. A single model instance serves all construction arms.
- At most 256 output tokens for opportunity selection, 640 per construction and 512 for method learning. Individual dispatches cap at 256 tokens. Actual output usage is debited when available. Uncertain or invalid dispatches consume their reservation. Stop a construction after a complete development match, after an identical unsuccessful query repeats, or when fewer than 96 output tokens remain. Seal the earliest best-scoring candidate in incomplete runs. Retain every failed attempt in the local run chronology.
- Each mission has eight development cases and nine hidden-until-finished confirmation cases. The controlled cases vary IDs, inputs and order from a frozen seed. There is one public-source replay per mission. All arms receive the same objective, input schema and number of detailed development examples per call. A₁'s mission is excluded from the causal comparison. Freeze the cases, incumbents and source identities before asking the model for an opportunity.
- The confirmation grader checks exact row multisets and preserves each case outcome. A sealed candidate must match every development and confirmation case to earn the technical verdict. The conventional controls are direct SQL with sorting, window functions or recursive traversal. Independent Python computes the expected outcomes before construction. No participant, buyer, paid API, production automation or confidential record is involved.

| Arm | Intervention |
| --- | --- |
| Original | Original constructor presents development cases in the preregistered input order. |
| Ordinary | Retain the exact first artifact and policy, and run the policy on the full development pool for an ordinary fixed ordering. Subsequent failures draw from that order. |
| Augmented | The same artifacts and resources. Run the policy on the presently relevant cases with their current failure flags. |
| Withdrawn | The augmented constructor sees the same prior objects with the executable policy withdrawn. Use input-order development feedback. |
| Conventional | The preregistered independent SQL implementation. Compare under the same confirmation cases. |

The trial order reverses for the second fresh mission. Execute all registered comparisons, including ties and failures. Policy execution counts only when the SQL returns distinct admissible IDs. An executed policy can order the same two IDs as the input-order control. Record the difference separately. Keep the incumbent when it matches all cases and no complete productive gain has been established. Inventor improvement requires useful changes in selected cases and demonstrably better new construction at comparable total resource use against both ordinary reuse and withdrawal. This two-mission pilot can support only a local result. Repeated generational improvement and operational economics are separate gates.
