## Opportunity and inventor lineage

MONTREAL.AI needs to know which qualification work must be repeated when a published prerequisite changes. The 8B selector chose this opportunity from three registered public operating problems. It reasoned that tracing dependencies by hand risks leaving stale evidence in a release. It saw the opportunity briefs only. Its first construction was interrupted by the operator after the observed CPU throughput made the planned matched run impractical on this host. The original registration and reserved dispatch remain in the record. There is no cross-model superiority verdict.

I₀ in the [CPU cohort](RESOURCE-FOLLOWUP.md) was Qwen3-4B with a typed, read-only SQLite runtime and input-order development feedback. The model wrote an executable dependency query. It matched 1/8 development and 1/9 confirmation cases. The query did not compute the required transitive closure. A second attempt repeated it, and the registered stagnation rule stopped construction. The experimental A₁ was rejected. This episode allowed an exploratory learning step, without qualifying A₁.

R₁ was the next model-written query. It ranked already failing cases with at most ten input rows and at least one expected output row, favoring a large difference between input and output counts. I₁ added this query as a case-selection policy. The policy could be withdrawn while retaining the same prior content. All four model arms used the same model and output budget. Ordinary reuse evaluated the same retained policy over the full development set for a fixed ordering. Its failure flags were neutral during that ordering step. The augmented arm could evaluate its current failure subset. The original inventor received no prior. Each task had its own independently written conventional query and Python expected-output oracle.

## Diagnostic follow-up

On a separately [registered draw](DIAGNOSTIC-FOLLOWUP.md), the constructor saw the rows its previous query actually returned beside the expected development rows. The model reached 3/8 in development and 3/9 in confirmation. It still emitted a one-hop query and repeated it. The developer changed the feedback format. The model received no solution query. This cohort also changed the case draw, so the score difference alone does not estimate the effect of the feedback change.

The [larger-model follow-up](LARGER-FOLLOWUP.md) ran Qwen3-8B with reasoning enabled on a third frozen draw. It generated a query that attempted recursive traversal. SQLite refused it in every case. A second request returned no usable candidate. The larger-model artifact scored 0/9. The conventional query scored 9/9. The configuration and cases differed from the 4B trials, so this is a separate construction result.

## Observable resources

The 8B opportunity call took 147.73 seconds, with 197 input tokens and 75 output tokens. Its interrupted construction has a reserved 256-token bound and unknown actual usage. The 4B CPU cohort made 19 local requests, with 15,623 reported input tokens, 2,198 output tokens and about 632.5 seconds of request wall time. This includes the rejected constructions and the policy-learning request. The diagnostic trial took two requests, 1,261 input tokens, 156 output tokens and 47.41 seconds. The larger-model follow-up took two requests and 130.46 seconds. The first request reported 502 input and 224 output tokens. The second used its 96-token reservation, with actual usage unreported. The three conventional confirmation evaluations took approximately 2.6–4.7 ms each in the CPU cohort. Those timings measure different steps. Complete accounting for operator setup, human labor, hardware, energy, maintenance and productive consequences remains open. There was no real-member observation, paid inference or commercial transaction.

## Reproduce and challenge

From the released companion, run `python3 reproduce.py`, `python3 reproduce.py --diagnostic` and `python3 reproduce.py --larger` without a model. The frozen evidence includes exact running units, case commitments, instantiated prior digests, developmental comparisons, selections and all final assessments. The verifier recomputes the developmental and confirmation results. To run the CPU study again with a local model, use `study/run_pilot.py` and the [bilingual companion guide](../../products/frontier-member-tools/inventor/README.md). The replay files hold normalized data so evaluation remains usable after a public Pages snapshot changes.

Study code and data were operated by one developer. Confirmation cases stayed outside constructor prompts and entered a separate evaluation command after construction. No confidential records were used. The separately administered evaluation and protected delivery boundaries remain under issues #565 and #550. Opportunity selection, source projection, public controls, budgets and runtime definitions were supplied by the operator. SQL proposals and the case-ranking query came from actual model responses.
