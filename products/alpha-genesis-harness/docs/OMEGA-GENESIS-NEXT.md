# Ω GENESIS NEXT / Ω GENESIS NEXT

**Investigate an improvement to the HARNESS, construct a bounded candidate, and keep only what the evidence supports.**

Ω GENESIS NEXT is an internal engineering workspace. Its first experiment targets the actual HARNESS acceptance path: can an evidence index avoid repeating unchanged checks while still rejecting stale, changed or misleading inputs? A second task examines experiment selection using the retained mechanism. The experiment is allowed to fail or tie with conventional reuse.

## Start in the application

1. Extract the complete download and start the source launcher for your operating system. Python 3.10+ is required; Docker and a model API key are not required for this bounded experiment.
2. Open **What could GENESIS itself become capable of next?** on the Start screen, or choose **Ω GENESIS NEXT** in navigation.
3. Inspect current capabilities. Read the distinction between an implementation, an executed test and a capability independently verified within a stated scope.
4. Find shared bottlenecks. Review the affected opportunities, dependencies, assumptions and construction choices. Estimates are planning inputs, not earned revenue or measured benefits.
5. Inspect the bounded evidence-reuse proposal. Authorize that experiment explicitly, then choose **Construct and challenge the upgrade**.
6. Inspect the existing route, candidate and competent ordinary-reuse comparison. Read the successor result and complete-cost limitations before treating a measured reduction in checker calls as an economic improvement.
7. Export the Ω evidence. Retain the result, protocol and source identities together. A saved result is not a new live experiment.

This workspace needs the local connector. Opening `app/index.html` directly still supports the existing browser/manual workflows, but cannot silently create private server-side experiments or persistence.

## What gets constructed and tested

The candidate extends the existing workflow checker with a dependency-aware evidence index. Construction writes candidate source to an isolated workspace; it does not overwrite the installed HARNESS. The evaluator and acceptance protocol stay outside the candidate's modification scope.

The comparison includes the current checker, the candidate and ordinary competent reuse with the same relevant information. Changed inputs, changed checks, changed dependencies and invalid transfers must not inherit stale acceptance. Independent checking validates behavior against the declared protocol rather than accepting the candidate's own success assertion.

The successor is a different internal operation: selecting verification work under a declared resource constraint. A lineage record identifies which retained mechanism was used, its conditions and the observed result. Merely running the second experiment after the first does not prove that the first enabled it.

The built-in construction recipe is authored and finite. It is not evidence that a model independently invented this algorithm, that this is a novel caching method, or that GENESIS can safely rewrite arbitrary production code. Authorization covers the isolated experiment, not deployment, credentials, purchases or changes to the evaluator.

## Capability map, vault and frontier replay

The capability map records implementation, requirements, limits and evidence separately. The Possibility Vault preserves deferred opportunities and their missing capabilities. Shared-bottleneck discovery considers which missing means recur across opportunities, without counting forecast successor value as realized value.

A frontier observation can trigger reconsideration of a vault entry. An observation marked reported remains a report until tested. A matching phrase, model release or source URL alone does not remove an engineering obstacle. Replay proposes a targeted test; it does not certify the opportunity as feasible.

The [Frontier Monitor](FRONTIER-MONITOR.md) can periodically observe explicitly allowed public sources while the connector runs, then replay new hashes as reported observations. Restart consent is separate.

Keep source timestamps, provenance and uncertainty. Connected research requires separately authorized data access. This local demonstration sends no inference or frontier-retrieval requests.

## Reproduce from the command line

From the extracted product directory, use a new private workspace and an output location you control:

```sh
python3 -m bridge.genesis_next demo \
  --workspace /absolute/private-omega-workspace \
  --authorize \
  --output /absolute/OMEGA-RESULT.json
```

On Windows, use `py -3` in place of `python3` and native absolute paths. The commands below inspect existing state:

```sh
python3 -m bridge.genesis_next status --workspace /absolute/private-omega-workspace
python3 -m bridge.genesis_next discover --workspace /absolute/private-omega-workspace
python3 -m bridge.genesis_next export --workspace /absolute/private-omega-workspace
```

The release qualifier runs the experiment against an exact verified archive in a fresh temporary directory. See [release verification](RELEASE.md). The [fixed protocol](../evidence/OMEGA-PROTOCOL.md), implementation and independent tests are included in the download.

For the separate fresh-instance successor comparison, freeze the candidate and evaluator before generating new cases:

```sh
python3 scripts/qualify_genesis_successor.py freeze --output /absolute/OMEGA-FREEZE.json
python3 scripts/qualify_genesis_successor.py run \
  --freeze /absolute/OMEGA-FREEZE.json \
  --output /absolute/OMEGA-FRESH-SUCCESSOR.json
```

The [supplementary protocol](../evidence/OMEGA-FRESH-SUCCESSOR-PROTOCOL.md) fixes the generator, alternatives and acceptance rules. A new nonce creates previously unseen instance values only after the source freeze. The receipt retains that nonce, exact cases and all four arms. Fresh instances of this declared task are distinct from an unseen external task family. The ordinary content-addressed control receives the same inherited information and may tie.

The [equality-corrected source revalidation](../evidence/OMEGA-REVALIDATION.md) preserves the same scientific conclusion: candidate and ordinary reuse both correctly adjudicated 32 successor cases using 20 new checks and 12 reuses, after 24 initial checks. Uncached and inheritance-withdrawn arms adjudicated 20 cases under the same successor allowance. All arms made 44 total checks; full economic costs remain unknown. Earlier receipts are retained with their original source identities.

## Reading the outcome

| Result | Meaning |
|---|---|
| Scoped checks pass | The observed construction satisfied those particular checks. |
| Fewer repeated checker operations | A measured computational difference in the declared workload. |
| Ordinary reuse ties | No advantage over that capable conventional method was established. |
| Unknown engineering, maintenance or host cost | Complete economic benefit remains unestablished. |
| Candidate rejected | Preserve the failure and its cause; do not activate the candidate. |
| A successor uses the capability | A dependency was exercised; a comparative advantage still requires the controlled result. |

A complete-cost advantage needs the construction, testing, transfer, maintenance, execution and failure costs relevant to the chosen horizon. Included execution does not establish zero economic cost. Timing measurements are host-specific and can be noisy. Technical acceptance, economic advantage, scientific novelty and production promotion remain separate decisions.

## Français — premier parcours

**Étudiez une amélioration du HARNESS, construisez une version candidate limitée et conservez ce que les preuves permettent réellement d'établir.**

Décompressez le téléchargement, puis lancez le connecteur local avec Python 3.10+. Ouvrez **Que pourrait GENESIS devenir capable de faire ensuite?**, ou **Ω GENESIS NEXT** dans la navigation. Inspectez les capacités, recherchez les obstacles partagés, puis lisez la proposition et ses limites avant d'autoriser l'expérience. Examinez les trois méthodes comparées, le résultat de la tâche suivante et les coûts encore inconnus. Exportez ensuite les preuves.

L'expérience construit une modification isolée du vérificateur réel. Un index de preuves cherche à éviter les vérifications inchangées, tout en refusant la réutilisation d'une acceptation périmée. Le code candidat ne remplace pas l'application installée et ne modifie pas ses critères d'évaluation. Une seconde tâche étudie la sélection des vérifications avec la capacité conservée.

La recette est préparée, finie et reproductible. Elle ne prouve pas qu'un modèle a inventé l'algorithme de façon autonome. La comparaison autorise une solution ordinaire compétente à gagner ou à égaler le candidat. Une économie d'opérations ne prouve pas un bénéfice économique complet lorsque les coûts de construction, de transfert ou de maintenance ne sont pas mesurés.

La revalidation sur le code corrigé conserve l’égalité avec la réutilisation ordinaire : les deux méthodes jugent correctement 32 cas suivants avec 20 nouvelles vérifications et 12 réutilisations, après 24 vérifications initiales. Aucun avantage en coûts complets n’est établi.

Le coffre de possibilités garde les obstacles et conditions de réexamen. Une nouvelle observation peut proposer une expérience; elle ne prouve pas que l'obstacle a disparu. Les observations rapportées, les tests exécutés et les résultats indépendamment vérifiés demeurent distincts.

Les commandes ci-dessus fonctionnent depuis le dossier extrait. Sur Windows, remplacez `python3` par `py -3`. La démonstration locale ne demande ni Docker, ni clé API, ni requête d'inférence externe. L'autorisation concerne uniquement l'expérience isolée; elle ne permet ni déploiement, ni paiement, ni changement de compte ou de critères.
