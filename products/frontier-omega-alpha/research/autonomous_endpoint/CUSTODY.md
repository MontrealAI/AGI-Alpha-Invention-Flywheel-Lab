## Activate on approved hardware once

1. The repository owner uses a separate local macOS administrator credential to create a non-login, non-admin `frontier-evaluator` account and exclusive read group. Keep that credential and the offline Ed25519 authority key outside both the constructor and this service account. Stage the bootstrap and its imports, Python runtime and OpenSSL in an administrator-owned protected location. Bind the exact host with administrator-owned `host-binding.json` and its digest. Its `hostname` must agree with the local machine. Set private paths below only after this host is approved.
2. Keep `/Library/FrontierEvaluator` root-owned and non-writable by the evaluator or constructor. Use two subdirectories `approved-code` (only independently approved source files, exact digests) and `cleared-records` (only exact read-only input hashes, with no access for other users). The approved entries include the versioned operational requirements rather than a lab proxy. Record-owner approval includes correct context, scope, cutoff, source rights, resource caps, price/cost provenance and retention. Stage no actual workload until the clearance is documented. Before that, run a canary with #449 public fixtures and demonstrate effective denial of case/key reads and updates from the actual constructor identity and credentials. Confirm group and ACL membership on the actual host.
3. Give only the evaluator use of `/private/var/db/frontier-evaluator` (0700) and its established `evaluator.key` (0600). The independent owner maintains the current signed `authority.json`, in the same envelope format as the public cycle's Ed25519 receipts. Sign it offline and distribute the owner key fingerprint and current authorization through an independent channel. Keep a separate protected append-only location for signed redacted aggregate receipts. The issuer must use two distinct keys. The evaluator runner gets its own key, no approval key, deployment credentials, billable access or constructor permissions.
4. Schedule the fixed evaluator command with one `launchd` service `ai.montreal.frontier-evaluator`, `UserName=frontier-evaluator`, using the owner's approved interval and CPU, storage and network settings. The job checks newly signed leases and processes each exact lease once. Invoke `--cleanup` first on each wake, then qualification or scoring. Cleanup applies only to expired service-created case directories under the signed host/identity/store binding. The source owner separately retires its read-only staging files. An expired or revoked lease prevents new scoring and receipt acceptance. Revocation disables the service and access, and provides replacement signed trust status to recipients. A receipt publisher must take the current authorization from the independent owner, never from the receipt's signer alone.

## Signed payload and execution

| Signed field | Authority |
| --- | --- |
| `schema`, `purpose`, `state` | `frontier-omega-alpha/evaluator-standing-authority-v1`, `non-production-only`, `ACTIVE` or revoked |
| `valid_from`, `valid_until`, `retention_days` | Dated owner-approved lease and retention. The request proposes at most 30 days or the shorter source right. |
| `host_binding_sha256`, `evaluator_user`, `evaluator_uid`, `evaluator_gid`, `constructor_uid` | Approved host and separate dedicated identities. `constructor_uid` is `null` for off-host construction with no local account or credentials. |
| `private_state`, `aggregate_directory`, `evaluator_key_sha256`, `revoked_key_sha256` | Private key and case scope, bound export directory, current signer and revocation list |
| `python_sha256`, `code_sha256`, `score_entry`, `records_sha256`, `operating_requirements_file` | Independently approved exact interpreter, scorer and record version |
| `run_wall_seconds`, `new_spend_authorized`, `publish` | Approved bound, `false` for new spending, and `signed-aggregate-only` |

Run `standing_authority.py` under the evaluator identity with `--authority-root`, `--private-state` and `--owner-trust-sha256`. Use `--output AGGREGATE_DIRECTORY` to score and sign one approved lease, or omit it for readiness discovery. The executable scorer receives the read-only cleared-input directory and its own case directory as positional arguments. Its only public output is the four integer counts `accepted`, `abstained`, `cases`, `rejected`. Scorer stderr and raw case evidence stay private. The runner invokes only approval-bound scorer code and validates the active lease again before signing. For a recipient use `--verify-receipt RECEIPT --active-approval CURRENT_APPROVAL --owner-trust-sha256 OWNER_FINGERPRINT`. Keep superseded scientific receipts as historical evidence. Current validation binds a receipt to the current, unexpired authorization and signer.

The actual owner inventory, root authority, case and administrator denial, installed runtime, device power/recovery behavior and network controls remain untested on the Mac. The three local qualification tests exercise distinct Ed25519 owner/evaluator keys, revocation and expiry, aggregate disclosure rejection, and expiry cleanup only in generated case directories. They do not establish actual operating authority. The production release and the confidential trial remain gated separately.
