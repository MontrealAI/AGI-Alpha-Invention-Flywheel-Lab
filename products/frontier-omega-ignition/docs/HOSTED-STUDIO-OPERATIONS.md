## Service boundary

The public HTTPS origin exposes only the introduction, a curated static demonstration and the Studio sign-in shell. Private APIs require a one-use invitation exchanged for a secure, HttpOnly, same-site cookie. Each invited workspace has its own SQLite store and queue. The installed trusted interpreter executes only data-language operations. Historical native, filesystem-specific or network specialists are excluded from the hosted mission schema. Public release discovery uses curated publisher feeds only with the mission's public-source grant. The provider is an operator-configured local process; user input cannot provide an endpoint, credential, external payment or shell command. The local legacy workbench remains a separate loopback-only entry point. Public Pages can host the curated content alone.

Keep production and staging on separate hosts or service users, separate protected directories and independent HTTPS origins. The database stores the environment at creation and refuses to open in the other environment. Keep transaction credentials, local wallets and unrelated private documents off the service host. The Python model process and web worker share an operator trust boundary; business inputs must be suitable for that operator. Do not put live access credentials in mission text, evidence or screenshots.

The service unit grants write access only under `/var/lib/ignition` plus its private temporary directory. The HTTP listener binds only to loopback. Use the relevant existing provider options from `MODEL-ROUTES.md` and the exact release qualification. Hash the model weights on that host. Pause or stop an independently authorized running mission from the Studio before revoking when the work itself must stop. Pause/stop takes effect at the next safe checkpoint. A local call already in flight can still return its receipt. Stage and production credentials do not cross.

## Check, recover and roll back

* **Health.** Run `python3 -m ignition.hosted_monitor --state /var/lib/ignition/production --origin https://APPROVED-HOST --port 8784`. The local probe checks readiness through the exact configured Host and reads durable queue ages and free disk. It returns a failing exit on a problem and prints the matching operator action. The timer writes to the system journal. Route unit failures through MONTREAL.AI’s approved alert channel; separately monitor the public TLS path from outside the host. A healthy local process cannot verify public DNS or certificates. Use per-mission events and consented, local inspection for diagnoses. Private audit rows in `access.sqlite3` capture invitation issuance, session creation/closure and revocation without raw codes or payloads. Each workspace's private mission database records the admission time of every accepted revision in the transaction that created it.
* **Dependency or worker failure.** Pause affected work. An unavailable model produces a blocked mission and no synthetic answer. Restore the pinned dependency, verify readiness and resume the same mission within its remaining allowance. After a worker restart the persistent queue rechecks active queued/running revisions and skips cancelled work. Durable mission events retain completion, retry and failure evidence. Investigate blocked inventory through the entitled workspace. Preserve original failures before amending a mission.
* **Backup.** Stop the service, wait for the process to exit and run `python3 -m ignition.hosted --state STATE --environment production backup /PRIVATE-BACKUPS/NEW-SNAPSHOT`. The copy includes tenant data, evidence and auth metadata; store it encrypted outside the service volume under authorized retention. The tool refuses an active service, verifies SHA-256 for each file and SQLite integrity, and excludes process locks. For unattended operation use the optional backup timer below. The health timer reports a stale or missing receipt when backup monitoring is enabled.
* **Restore.** Prepare a separate private parent, then run `python3 -m ignition.hosted --state /PRIVATE-RESTORE/NEW-STATE --environment production restore /PRIVATE-BACKUPS/SNAPSHOT`. Use a fresh target. Verify counts, mission events, independent artifact digest and the same released code. Restores invalidate all login sessions and unredeemed invitations; issue new codes only after reviewing access. Restart on the restored directory after the operator approves the data cutover. Keep the previous state offline until reconciliation is complete.
* **Release rollback.** Before an update, retain the running release, stop intake, quiesce workers, take an encrypted backup and independently exercise the target against a disposable restored copy. The switcher supports state-compatible releases only. With the old service healthy again, run `python3 deploy/switch_release.py FULL_CANDIDATE_SHA --origin https://APPROVED-HOST`. It checks both Git checkouts, atomically switches the service symlink, restarts, and verifies readiness and served revision. A failing target restores and rechecks the previous source; the command still exits as a failed deployment. If schema compatibility is unknown, restore a verified compatible state to a new directory under incident control, capture post-backup changes and reconcile them before reopening. Never point the public proxy at the old unauthenticated local workbench. On the first deployment there is no existing hosted revision; rehearse rollback in staging and retain a maintenance/closed-ingress fallback.
* **Rehearse.** From the product root, run `python3 -B -m unittest discover -s tests -p 'test_hosted*.py' -v`. The suite exercises fresh per-tenant sessions, isolation, duplicate admission, rate/budget boundaries, invalidation, backup integrity and a real local two-checkout process switch. The switch test deliberately injects readiness failure on the second process and verifies that the first revision serves again. These local results cover the software mechanism. DNS/TLS rotation, host-specific service management, operator alert receipt and production rollback still require evidence on the approved deployment.


## Optional supervised backups

The packaged timer runs at 03:00 and 15:00 UTC with a short randomized delay. Enable it only after the duty owner prepares the volume and approves those brief maintenance windows. A separate encrypted Linux device-mapper (LUKS) volume is supported. The operator must confirm media custody, encryption keys, off-site copy and retention. This job never deletes old snapshots.

1. Mount the dedicated encrypted volume apart from the service state, create a subdirectory owned by the service user with mode 0700, and validate its mount and backing mapping independently. In root-owned `/etc/ignition/backup.env`, set `IGNITION_BACKUP_MOUNT` to the actual mount point, `IGNITION_BACKUP_ROOT` to that private subdirectory, and `IGNITION_BACKUP_DEVICE_ID` to the exact enrolled `CRYPT-LUKS…` mapping identifier from sysfs. These settings contain no decryption key. A disconnected, plaintext or different volume is refused before the studio stops.
2. Provision the root-owned regular mode-0600 file `/srv/ignition/.deploy.lock` shared with the release switcher. Install `deploy/ignition-backup.service` and `deploy/ignition-backup.timer`. In a systemd drop-in for the backup service under `[Service]`, add `ReadWritePaths=/exact/private/backup/subdirectory`. Make the installation and service configuration root-owned; the worker must not be able to change privileged code. Put `IGNITION_BACKUP_REQUIRED=1` in `studio.env` to activate missing/stale backup alerts in the minute-by-minute health check.
3. Run one supervised snapshot and restore drill on staging before enabling its timer. Verify that the Studio returns to readiness, login codes and certificates are issued through the intended controls, the new backup is on the intended volume, and alert delivery reaches the duty owner. During each copy the supervisor checks that the single designated studio unit is active; it never starts a service deliberately found inactive. It records the need to restart before it stops the unit. It restores that unit after success or failure; systemd's post-stop hook retries recovery after abnormal termination. A persistent restart marker requires immediate operator inspection. Monitor the model-backed readiness endpoint after maintenance; a systemd active process alone does not prove a functioning model.
4. The unprivileged backup worker pins the open destination directory while copying. A verified SQLite and SHA-256 snapshot creates a local success receipt. A missing receipt, one over 24 hours old or a future-dated receipt triggers the monitor's actionable alarm. Restoring state clears the backup receipt and invalidates sessions. This receipt times the last verified copy; it cannot prove that external media still exists or that off-site recovery works. If a backup fails or the volume fills, retain old snapshots until the operator makes a retention decision.

## Authority throughout a mission

Restart, resume and a repeated intake identifier all preserve a revision's stored call counter and acceptance criteria. A counted call consumes a slot before the provider is invoked. A completed cached call reuses its receipt. An interrupted call without a completed reply can consume another slot only within the remaining allowance on an authorized retry. Pausing or restoring the same revision cannot replenish it. Explicit amendment creates a new revision with its own separately approved allowance; the eight-call ceiling applies per revision, with the daily workspace admissions limit across accepted revisions. The US$0 paid-provider restriction applies throughout. Previously incurred local compute remains an economic cost on every retry or amendment.

For llama.cpp, matching a live server alias and a configured SHA-256 is a readiness signal. It cannot establish that the serving process loaded the file the operator hashed. Before enablement and after each model restart, verify the on-disk weights digest, bind the model server's reviewed launch command to that immutable path and alias, control who can replace its executable, weights or local listener, and attach that evidence to qualification. Without that evidence, keep the model identity and release gate unverified even if `/readyz` returns 200. Ollama additionally checks the installed manifest digest returned by its local service; trust in that operator-controlled process remains necessary.
