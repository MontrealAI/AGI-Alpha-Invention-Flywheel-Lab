# Native business-design search 041 — executable, bounded enterprise experiment

## Purpose and scope

This opt-in controller **runs the repository's authoritative \`connected_enterprise.engine.run_world\`**, using the actual mandatory adaptive \`Account\`, \`JournalAccount\`, source manifest, native customer choice, producer/checker, acceptance, payment, earned-only investment, checkpoint and independently reconstructed native audit. It does not create a second ledger, use future forecast cash, rewrite the default operating policy or claim real commerce.

It searches a **joint finite policy space**: currently supported baseline, channel, earned-funded growth and competitive-growth arms, optionally combined with independently validated existing strategic price/method/allocation/channel policies. These combinations are *business designs and means of delivering them*, not a generative proof that the machine can invent arbitrary new services. Current native outcomes remain reconciliation, KPI reporting and evidence matrices.

The controller selects a candidate using **observed development-world profit, obligation protection and actual collection** (including native production/setup and failed bid costs) rather than a developer-supplied winner, simulated forecast revenue or a manufactured win rate. A losing or unprofitable challenger may lose to the incumbent; if every candidate loses or lacks protected profit the result is **no qualified investment**, not a forced promotion.

It then freezes that selected design and runs it with a new predeclared seed alongside the strongest declared incumbent, using the same simulated market, capital and source. It independently re-audits every completed native world. Within the chosen confirmation world, a source-linked witness must show:

1. A first independently accepted and collected profitable order.
2. A **later** native earned-funded acquisition or capacity commitment, with preserved protected reserves.
3. A subsequent independently accepted/collected order tied to that actual native investment plan.
4. A different customer or complete service outcome and **positive collected order contribution net of the actual source-linked investment invoice**, with positive overall native enterprise complete-cost profit. A higher per-order margin is reported only as a separate diagnostic.
5. A matched baseline comparison with positive incremental complete-cost profit to claim superiority on this particular fresh seed.

No single development run is statistically sufficient to prove out-of-sample generality; this is a small execution demonstration. Better per-order margin does not, by itself, prove positive lifetime contribution of the investment. No separate native account's funds are pooled into another account. The comparison is an explicitly conditional, simulated synthetic business.

## Reproduction

From the repository root with the dependencies in \`requirements-commercial010.txt\` installed:

\`\`\`sh
python3 -m unittest -v tests.test_connected_design_flywheel041
python3 -m connected_enterprise.design_flywheel demo --output /absolute/new/design041
python3 -m connected_enterprise.design_flywheel verify --output /absolute/new/design041
\`\`\`

The fixed \`demo\` spec uses openly exposed synthetic customer assumptions and **three real native policies**, with development seed 341014, fresh seed 341015, 14 operating days, eight finite customers and no actual sales. It is for engineering reproduction, not a hidden confirmation or a billion-dollar projection.

For an independently registered finite experiment, write the exact JSON contract returned by \`example_spec()\` (including complete native market configuration, designs and predeclared seeds), then run:

\`\`\`sh
python3 -m connected_enterprise.design_flywheel run --spec /absolute/spec.json --output /absolute/new/business-search
python3 -m connected_enterprise.design_flywheel verify --output /absolute/new/business-search
\`\`\`

**Output**: local \`SPEC.json\`, \`SOURCE.json\`, \`SERVICES.json\`, native per-world \`RESULT.json\` and \`AUDIT.json\`, \`INDEX.json\` and **compact \`PUBLIC.json\`**. Keep the local output private: it contains source-bound account records and private simulation credentials in the runtime, even though it does not make any real monetary transfers. Publish only \`PUBLIC.json\`, which includes measured simulated cash/profit, designed comparison, source IDs and any bounded source-linked witness, never private account files. No claims without independent re-audit.

The qualification workflow \`.github/workflows/native-design041.yml\` runs a clean exact-source demo, independent verify, and a fail-closed gate for **both** a positive-net earned-funded successor and a positive matched incumbent comparison. If either is absent, retain the negative result; never cherry-pick another seed, weaken a threshold or change the confirmation pair.

## Boundary and next native engineering step

This first increment is a **native executable policy search and evidence gate**, not a replacement for the active complete-offer work in PR #65, recurring buyer income PR #72, capital maturity, or release PR #74. Only the incumbent enterprise owns actual financial actions; this branch changes no default financial policy.

The next design-search extension should run on top of the qualified complete-offer menu and replenished buyer pipeline, then implement a **within-account adaptive search over offer/service/production/verification/partner/retention actions** using real (or explicitly modeled) observed responses, source-bound policy updates and independent replay. Keep external buyer values private to the environment. A proved chain should then show that the machine **selected and executed** the second design because the first produced the necessary funds or reusable capability—followed by matched causal ablations and complete cost of search. No arbitrary generator should declare new demand or sufficient capacity from a profit forecast.

In this implementation, the native enterprise already chooses acquisition/capacity actions at successive events from actual prior accepted orders, while the outer controller selects the next native operating policy from observed prior worlds. The supported conclusion is therefore narrower than general autonomous business discovery or open-ended recursive invention.

### Lessons

- **Tried:** Joint selection of current native commercial policy alternatives under an unchanged public market.
- **Outcome:** Require actual independent native audit and source-linked funded successor, not a descriptive economic story. Hosted exact-source evidence is the arbiter.
- **Why/unknown:** Buyer values and agent/host billing are authored or unmeasured; price competition and long-horizon generalization remain unresolved.
- **Next/avoid:** Integrate qualified complete-offer and recurring distribution capabilities after their owners' changes are safely merged; avoid second ledgers and retrospective favorable-world selection.
