# Prospective development-example repair

Registered after the first continuation cohort exposed a recurring failure on its public editorial migration. The primary trial and its failed attempts stay frozen. No observation from the new repair method is used to set any gate below.

**Question.** When a rejected proposal agrees on much of a task but applies the wrong string operation, can one real Qwen repair, informed by field-level discrepancies on already disclosed development examples, produce a receiver that passes the unchanged independent test?

| Item | Registered choice |
|---|---|
| Dataset and comparator | Use exactly the migration fixture, purpose, public demonstrations, hidden confirmation cases and independent evaluator of the registered three-route comparison on product commit `4719005c` (PR #441). Recompute the public conventional baseline on the same contract. |
| Historical starting program | Reconstruct the direct arm's second proposal with canonical response SHA-256 `9353460cae209c5ee2e7aa43d9b45bcc93fa77136c8743391cb9ffa106e3ed2e`. First re-evaluate it. Require the identical contract, rejection and five of nine passed checks before creating any new model observation. Preserve discrepancies as a blocked experiment. |
| Intervention | Show public development mismatches with proposed output/error and expected output per target, plus supported direct or delimiter/position alternatives when they fit every public development row. Report ambiguity explicitly. The only permitted held-out information is the pre-existing aggregate failure count by check group. Do not transmit held-out inputs, expected values, case names, row hashes or individual pass/fail observations. |
| One new model cell | Use one genuinely generated repair proposal from the previously pinned Qwen3-4B-Instruct-2507 Q4_K_M and llama.cpp CPU route, on an eligible standard public runner. Start with the archived rejected proposal, label its origin, and make exactly one fresh `repair` inference on the revised source. No fixture response may satisfy the model stage. Retain the new verdict even on failure. |
| Primary endpoint | Independently acceptable construction, all original cases and controls, accepted conventional comparison and successful external recipient verification/example using the delivered program. A blocked run, malformed output, altered contract or failed receiver is not a success. |
| Additional arms | Separately test the opt-in ordinary public-example specialist, if implemented. Restrict it to declared projection and single-field split operations, prefer the simplest fitting family, abstain on ambiguity or unsupported mappings and independently verify any proposal. No fresh inference can be attributed to this arm. Run fresh-schema unit controls for middle/last components, ambiguous hypotheses and private-acceptance visibility. |
| Evidence and cost | Record exact product, evaluator, workflow, model and runtime identities, old and new response hashes, elapsed times, tokens and resource limits, acceptance, recipient outcomes and conventional results. The public examples were already known to the model; private acceptance stays frozen. Complete economic costs are unmeasured. |

The new trial is conditional on a publicly known failure and uses the same mission. A repaired program would demonstrate a specific technical correction. It cannot establish an independent fresh-task success rate, attribution solely to feedback against an unmatched counterfactual, a historical frontier crossing, general discovery advantage or paid demand.
