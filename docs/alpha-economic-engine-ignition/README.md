# ALPHA Economic Engine — First Ignition 0.1.0

**A working autonomous production core, not a demonstrated self-financing enterprise.**

This adds a narrow persistent workcell to `connected_enterprise`: one worker discovers local submitted workloads, constructs candidate database indexes, tests them, publishes reversible SQL artifacts and retains a successful configuration for a fresh successor. It can continue receiving work without a person invoking each cycle.

The first executed demonstration uses three synthetic databases of 80,000 rows each. Computation, indexing, result checking, process persistence, delivery and reuse are real. Customers, market discovery and monetary settlement are **not** demonstrated. The workcell uses established SQLite methods, not a frontier model or a new indexing algorithm. It is supporting infrastructure for FRONTIER COMPOUNDER Ω, not admission of a routine optimizer as the Blue Sky flagship.

## Run the machine

Python 3.10+ and POSIX (Linux/macOS); no pip packages, paid APIs or model keys. Linux/Python 3.13.5 was exercised here; macOS is not yet qualified. Run from a repository checkout or the supplied source bundle:

```sh
python3 -m unittest discover -s tests -p 'test_alpha_runtime_ignition.py' -v
python3 -m connected_enterprise.alpha_demo --output ./alpha-demo
python3 -m connected_enterprise.alpha_runtime --root ./alpha-demo/machine audit
```

Use a **new** output directory for the finite demonstration. The demo actually starts one daemon, submits three jobs over time, waits for outcomes, checks a fresh cold-search control, audits delivered artifacts, tests a no-op restart and stops the daemon. It is not left running after the demonstration.

For continuing owner-controlled operation:

```sh
python3 -m connected_enterprise.alpha_runtime --root ./alpha-machine run --watch
```

From another terminal, submit a workload snapshot and its contract:

```sh
python3 -m connected_enterprise.alpha_runtime --root ./alpha-machine submit \
  --database /absolute/owner-controlled.sqlite --request /absolute/request.json
python3 -m connected_enterprise.alpha_runtime --root ./alpha-machine status
python3 -m connected_enterprise.alpha_runtime --root ./alpha-machine audit
```

`audit` obtains the single-writer lock; stop the watch worker before running it. SIGINT/SIGTERM finish the current work item and stop. A killed process releases the OS lock; a subsequent `run` recovers an interrupted item. Interrupting a computation can repeat that attempt: **at-least-once computation, one committed delivery record**, not exactly-once physical execution. Costs of an interrupted, unmeasured attempt are marked unknown.

## A usable output, not just a report

Each accepted job produces `outbox/<job-id>/apply.sql`, `rollback.sql`, `receipt.json` and `REPORT.html`. The source database is never modified. SQL deployment into a real database is deliberately not automatic: write overhead, storage, availability, deployment permissions and the complete production workload need qualification first.

The supported request is intentionally precise: an ordinary SQLite table, one to three integer equality fields, one integer range field, and an integer sum/count aggregation. Data must be non-null integers and the absolute sum must fit SQLite's integer range. Other workloads are not supported yet. The request includes disjoint discovery/confirmation parameter sets, minimum work-reduction factor and a declared index-storage allowance.

The example request is generated by the demo as `REQUEST-example.json`. It describes columns `tenant`, `status`, `epoch` and `amount`; adapt the names and parameter values to a schema within the supported contract. Identifiers are constrained and values are parameterized; no arbitrary SQL, shell commands or generated Python are accepted from jobs.

## The measured demonstration

| Case | Result | Candidate index configurations | Read-work reduction versus submitted database |
| --- | --- | ---: | ---: |
| First 80,000-row workload | Delivered, awaiting settlement | 8 | 2,018.26x |
| Fresh successor, different data | Delivered, awaiting settlement | 1 | 1,937.32x |
| Already conventionally indexed workload | Declined | 9, including failed reuse attempt | 0.994x |

**Both accepted outputs tie the conventional equality-first covering-index control (1.00x).** The large factors compare with the deliberately unindexed input databases, not with competent database engineers or another frontier AI. These are counted SQLite VM instructions on four declared confirmation probes, not bill reductions or general production-speed guarantees. Wall timings are separate, warm-cache, single-process observations and are noisier.

On the identical fresh successor, cold search tested eight configurations; validated ordinary reuse tested one. Measured `solve()` CPU fell from about 1.219 seconds to 0.724 seconds (40.6%) in that run. This excludes the worker's additional verification/audit and initial software development; it is not a complete-cost margin. It demonstrates ordinary reusable configuration, not improved inventive intelligence. A new machine may produce different timings.

The local suite passes **27 tests**, including a real worker-process kill and recovery, crash after verification, delivery I/O failure, duplicate submission, competing worker lock, unchanged original databases, changed inputs, forged answers, forged work metrics, SQL tampering, fake payment assertions, source identity, JSON/identifier validation and non-improving-work rejection.

Compact result receipts identify the executed source bytes. The first coarse-measurement attempt and its unsuccessful tie-break repair are preserved in `CORRECTION.json`; changing to per-instruction measurement fixed the specific regression. Reusing the same authored workload is a correction/regression, not fresh scientific confirmation.

## What each engine stage means here

- **Discover:** scan an owner-controlled local inbox. No autonomous market research, lead generation or buyer discovery.
- **Construct/test/deliver:** execute bounded authored index search, compare a competent conventional alternative, check results with a separately implemented Python row reducer, publish local artifacts.
- **Retain/advance:** retain an applicable index configuration and revalidate it on fresh work. This is ordinary reuse, not arbitrary code self-modification or a demonstrated frontier-expanding discovery.
- **Earn/reinvest:** deliberately **not connected**. Accepted jobs remain `DELIVERED_AWAITING_SETTLEMENT`. The runtime cannot turn an invoice, hash, local test or user-supplied payment assertion into revenue.

There is no second financial ledger. `work.sqlite` contains jobs, capabilities and event records, never balances or earned capital. Existing `JournalAccount` and adaptive `Account` remain the canonical financial mechanisms and are not modified or connected by this patch. Real demand/acceptance, an authorized payment/settlement integration, full cost and obligation accounting, and native funded reinvestment are outstanding. No self-financing commercial loop is claimed. In this run: **zero real customers observed, zero money collected, complete-cost profit unknown**.

## Integrity and deployment boundaries

A process lock prevents competing workers. Inputs are content-bound snapshots. The verified payload is committed before file delivery, so a publication interruption can resume without rebuilding the result. Events form a local hash chain; it is not a signature, proof of inference or external attestation. An owner who controls all files can rewrite history. `audit` replays checks against the actual inputs and source bytes; it is not independent institutional certification.

This is an owner-controlled local tool, **not a network-facing multi-tenant service or hostile-code sandbox**. The work directory must be private (0700); symlink paths are refused. Do not expose it to untrusted users or place private customer data in public GitHub artifacts. Confirmation cases are supplied by the owner, not cryptographically hidden. Revalidation does not guarantee correctness for unseen workloads. Index build time and storage are recorded, but write amplification, operational risk, maintenance, real billing, customer acquisition, taxes and support are not measured or funded here.

The worker has no runtime model inference, automated AI-frontier feed, generalized opportunity invention, external customer delivery, paid acquisition or live payment function. Its mechanism is an implemented production dependency, not the entire long-term ALPHA Economic Engine.
