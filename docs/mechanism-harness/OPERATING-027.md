## What is actually executed

The 026 finite mechanism compiler searches a three-operator ontology. The 027 adapter independently checks the exact source-bound plan and semantics before invoking real repository functions:

1. `commercial.onboarding.prepare_order` validates actual developer-supplied CSV inputs and produces the canonical synthetic order.
2. `commercial.service.deliver` constructs actual `reconciliation.json` and `exceptions.csv` in a fresh output directory.
3. `commercial.service_verifier.audit_delivery` independently recomputes row matching, conservation, and strict completeness. The adapter also checks the complete CSV exception schedule.

The 027 checker re-reads all three source files, the actual source module hashes, canonical prepared order, produced output, audit decision, and creates a scoped rederivation. Tampering with any of those or a stored permission/proof claim is rejected. An ambiguous payment with two equally plausible invoices is correctly **not** accepted under a strict completeness contract.

The concrete input and output authority is only `SYNTHETIC_PUBLIC_WORKLOAD`; the adapter contains no native finance operations, network calls, wallets, paid providers, customer credentials or real-value effects. Output directories are create-only. Incomplete executions are not silently upgraded into successful receipts.

## The three comparisons

- **Direct specialist:** call existing onboarding, production, and independent checker directly, with no mechanism planner.
- **Replanned composition:** recompute the typed symbolic plan for each task, then execute exactly the same P0 service methods.
- **Inherited composition:** re-use only a previously checked source-bound plan; re-acquire fresh current task input/output evidence and leave current proof/authority empty.

The three exposed developer-authored tasks cover complete two-customer matching, ambiguous unsatisfiable strict completeness, and a bundled invoice group. They are not a fresh hidden benchmark or a customer sample. This comparison is deliberately designed not to handicap the direct specialist. The methods should produce identical accepted outputs and errors; there is **no hypothesized saving** from wrapping the direct service in a mechanism planner. CPU and wall readings are actual process measurements in nanoseconds from the test host but exclude engineering, acquisition, independent institutional review, paid models and monetary costs. `STUDY.json` reports `causal_successor_inheritance_benefit:null` because the experiment is not a valid claim of general fresh successor advantage.

No extra billing should be added to the P0 service from these symbolic resource weights: those are **planning units**, not consumed dollars. This also avoids double-counting a pre-existing service's work as if an added planning pipeline performed it again.
