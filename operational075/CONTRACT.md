## K1 warehouse wave batching

The original input is `tasks/19_wave/problem/input/testdata/08.json`. Required output is `{"waves":[{"slot_id":SLOT,"order_ids":["ORDER"]}]}`. All 2,101 input orders must appear exactly once, with no splitting or unknown orders. Each wave admits at most four orders and 10,000 input SKU lines. Its exact typed slot must belong to every member's eligible slots, and slot wave quota must hold. Numeric slot `1` and string slot `"1"` are distinct. Source dates are provenance, not new constraints. The original objective is `unique_sku_lines / total_sku_lines - 1`; lower is better. Slots and wave count affect feasibility but are not objective penalties or tie breakers.

`client.verify_wave(source_root,input_path,artifact_path)` executes untouched original `verifier.verify` and `evaluator.evaluate` in a separate isolated Python process. Its accepted result is computational task acceptance, not an observed warehouse saving, physical production or buyer acceptance.

## K2 rolling fresh-grocery dispatch

The original task has three service days, GD01–GD03, each with six confirmation rounds. A policy receives only one current public window at a time. Future rows in `public/input/order_confirmations.csv` are organizer material, read only by the broker. Public customer attributes and directed road matrices remain available as in the upstream task. No new buyer, willingness to pay or market size is inferred from the task.

The policy interface is `decide(window,state) -> (submission,new_state)`. `state` starts as the registered initial JSON value, normally null; the policy must keep its own dispatched-order history. The broker gives no validity, score, route cost, dispatch confirmation or executed-order feedback during the episode.

The `window` object contains:

* `service_day_id`, `dispatch_round`, `ready_time`, `epoch`, `information_mode="rolling_batch_v1"`, `capacity=1000`, and `total_rounds=6`.
* `orders`: all orders confirmed for this service day up to the current round, including orders already dispatched. Each row contains `service_day_id`, its original `dispatch_round`, its original `ready_time`, `order_id`, `customer_id`, `demand`, `service_time`, `tw_start` and `tw_end`. These last two fields are exact aliases of upstream `window_start` and `window_end`; they are absolute seconds, not durations.
* `customers`: a mapping from integer customer IDs to the public attributes `customer_id,x,y,demand,service_time,tw_start,tw_end`. JSON wire keys are strings; the worker rehydrates this one mapping to integer keys before calling the policy. Customer zero is the depot.
* `duration`: the full directed integer-second matrix indexed by customer ID, with zero denoting the depot. The asymmetric matrix must not be replaced by Euclidean distances or a symmetric approximation.

The exact per-round submission is `{"service_day_id":"GD01","dispatch_round":1,"routes":[["ORDER_ID"]]}`. Empty routes means dispatch nothing. Every route departs at the current window's `ready_time`, waits if early, starts service no later than each order's `tw_end`, obeys capacity 1000, and returns by depot `tw_end`. A service-day order may be deferred until a later round if still feasible, but must appear exactly once by round six. Previously submitted routes and visit orders cannot be changed. The objective is mean directed driving time across the three days, excluding service and waiting time; feasibility precedes comparison.

## Immutable submission and acceptance boundary

`broker.run_episode(source_root,policy_module,output,initial_state=None)` is the execution seam. It calls only `operational075.ordinary` or `operational075.retained` in a separate process supplied with current window and its own prior state, a sanitized temporary code copy and clean environment. A Python audit hook refuses file/directory access outside that code copy and the Python/system runtime, all writes, subprocess creation and network activity. Future source/cache paths and broker output are outside its read allowance. Source cache and episode output additionally use mode 0700.

Development exposed an actual platform restriction: UID/GID demotion is denied in this capability-dropped execution namespace, and Landlock is unavailable (ENOSYS). The implementation therefore does not claim OS-user isolation or a sandbox against malicious native code. It relies on reviewed policy source, separate processes and audited Python file operations; policies use no native file-access bypass. This is stronger than passing future rows and asking the policy to ignore them, but is not external experimental blinding or a general hostile-code sandbox.

Each returned original JSON submission is stored with exclusive create as `periods/NN/SUBMISSION.json`, plus its state, byte hash, current-window hash, source/policy identities and chained receipt. The host locks the submission before opening the next window. It does not call upstream `RollingEpisode.commit`, which would return prohibited intermediate feedback. All eighteen original submissions are preserved, even if invalid. Resume checks hashes and history and never overwrites a locked submission. An interrupted incomplete period stops without silently retrying the policy.

The worker bundle is an explicit allowlist: `__init__.py`, `ordinary.py`, `retained.py`, `wave.py`, and `RETAINED.json`; an absent initializer is a bound empty file. Only existing declared source files and the retained content are copied. Later result JSON files are excluded. The host binds every copied byte, including retained JSON, before execution; it rechecks the bundle before every period and records its hashes in each worker receipt. Resume and independent audit require the same complete bundle, guard source, epoch, day, round, original byte count, window/state hashes and prior receipt before further work. Neither a changed retained document nor a relabeled receipt can silently advance the stream.

Only after all eighteen submissions are locked does `client.finalize_grocery` call untouched upstream `RollingEpisode.finalize_locked_submissions`, then original completed-context `verifier.verify` and `evaluator.evaluate`, in another process. This checks original per-round envelopes, payload identity, every order, release timing, capacities, time windows, depot returns and original objective. An invalid round is not corrected into a valid transcript. No checker or input is rewritten to obtain acceptance. `CLIENT_RESULT.json` records the final computational verdict, hashes and resources. This is not physical grocery delivery, actual revenue, newly economical demand or proof of an outlearning advantage.

The 18-period study and 16 MB worker payload allowance are finite experiment/resource contracts, not universal commercial scale limits. Actual process wall/CPU use is measured; those seconds are not invented human labor or measured dollar billing. Reproduction and independent checking may read the frozen source and all locked submissions after the experiment, but these later observations cannot be used to retune a procedure and relabel it as frozen confirmation.
