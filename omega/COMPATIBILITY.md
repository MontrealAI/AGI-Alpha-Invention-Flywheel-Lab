# Finite-state compatibility recovery: constructed buyer workflow

This edition constructs a portable behavioral substitute for a resettable,
deterministic local API from observations. The possible consequential outcome is
preserving an existing production workflow when implementation source is gone.
The executed cases are authored transaction-protocol simulators, not actual
orphaned industrial equipment. No physical deployment, safety, general finite
state bound or undocumented real-world compatibility is established.

The strongest complete alternative is conventional active automata learning
with equivalence testing and ordinary adapter construction. The implementation
uses that established approach. It does not establish an invention advantage.
The business must therefore earn its value through a useful complete edition,
voluntary choice and delivery economics; the seller simulation supplies those
separate assumptions and tests.

## Installation and first use

Python 3 standard library is sufficient; no dependency installation, model,
external account or internet connection is needed for the included workflow:

```sh
python3 -m omega.compatibility --output /absolute/new/compatibility-example
python3 /absolute/new/compatibility-example/runner.py start append commit
python3 /absolute/new/compatibility-example/compatibility.py --case queue_revision --output /absolute/new/fresh-adapter
```

The first command constructs and independently checks a four-state transaction
protocol from reset-and-query observations. The portable runner emits `opened`,
`appended`, `committed`. The downloaded learner constructs a changed protocol in
the final command, without importing the source repository. Each package carries
its adapter, runner, exact learner edition, documentation and SHA256 manifest.

The buyer journey is: preserve transaction behavior → compare conventional
learning and no change → establish the assumptions below → execute probes →
construct the state machine → independent fresh reset observations and longer
trace checks → inspect query/compute costs → use within the accepted scope or
stop. The learner cannot inspect the oracle's internal table. Its observation
table is closed and consistent before a candidate is constructed; concrete
counterexamples extend the table. Exhaustive testing is expensive as the state
bound increases. Sufficient resources are a prerequisite, not a promise.

## Buyer-supplied prerequisites

The buyer must establish permission, probe safety, a reliable reset, deterministic
responses, a finite input alphabet, an upper bound on relevant states, a stable
oracle version identity, and separate learning/verification query budgets.
These are explicit assumptions. Sampling cannot prove an unknown real system
has only four states. Unbounded counters, clocks, hidden external state,
concurrency, noisy output and unsafe reset invalidate the declared model.

For a buyer-owned local implementation, import `buyer_contract`, `ActiveLearner`
and `independent_acceptance` from the downloaded `compatibility.py`. Create the
contract with all four assumptions explicitly established, provide a callable
that resets and returns one output string for each input symbol, run `learn()`,
then check using a fresh callable. The library does not import or execute a
third-party implementation on the buyer's behalf. It includes no device driver,
external model router or physical reset instrument. Unknown assumptions require
further investigation or declining the activity.

## Acceptance and recovery

Independent acceptance ignores candidate success flags, cached observations and
learning-table conclusions. It checks package integrity, the exact executable
runner/learner edition, exhaustive fresh traces through length `2N−1`, repeat
reset behavior, and forty longer generated traces of length `2N+7`. For the
specified deterministic machines of at most N states, bounded exhaustive
comparison supplies the conditional equivalence argument. The longer traces are
excluded from learner queries; they are exposed authored tests, not external
blind validation. Repeated resets detect some faults, not every source of
nondeterminism.

Decline, unavailable oracle, unknown inputs, invalid permissions, contradicted
state bounds, query exhaustion, tampered outputs and malformed packages fail
closed. Graceful interruption stores observations bound to the exact contract
and oracle version. Repeated construction uses those observations; a changed
version cannot inherit them. Abrupt process termination may repeat safe reset
probes since the last checkpoint. This product checkpoint is not financial
authority. The native seller account separately protects orders and spending.

## Measured work and limitations

The three supplied protocols each use 3,280 distinct learner queries. Independent
acceptance performs 6,640 oracle calls, including repeated checks and forty
longer traces. One build therefore invokes 9,920 reset-and-query calls. A later
independent `accept_product` invocation incurs its additional verification work;
cache reuse does not make these checks free. Wall-time telemetry is machine
execution, not human labor, inference billing or a complete commercial invoice.
The seller model must price all relevant query, checking, acquisition, delivery
and obligation costs. Actual host/model billing remains unknown; zero paid model
calls is a different statement.

The successor test crosses two changed protocols with no inheritance, cash only,
retained probe content and ordinary equal-content reuse. All eight are accepted;
all require the same 3,280 learner queries and 6,640 independent checker calls.
Ordinary equal-content reuse ties exactly. These observations reject an extra
retained-method advantage for this experiment. They do not establish demand,
real migration savings, human productivity superiority or Super Alpha.

No continuing updates, personal support, unlimited inference or guaranteed
commercial outcome are promised. Buyer data never leaves the local test path.
