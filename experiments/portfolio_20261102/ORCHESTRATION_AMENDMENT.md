This amendment changes the scheduling of independent accounts. It changes no scientific threshold, economic recipe, capital, world, policy, account operation, cost, source-bound manifest, acceptance check, or native audit. The financial experiment remains frozen at commit `9d4b2a2efb0289d6493d24e2e6c9493720596971`.

## Reason and information available

Before this scheduling amendment's final freeze, the canonical serial run completed and independently audited the USD 25,000 and USD 100,000 central arms. The small-capital arm expensed USD 15,000 of research and refused the next unaffordable construction cost. The USD 100,000 arm reported USD 549,525 cumulative five-year modeled profit and USD 112,860 in its exact final 365-day window. These two outcomes were visible before the orchestration freeze; the remaining 22 accounts had not opened. The original serial process stopped at the root's intentional empty gate before arm 02, and the root removed only that verified-empty gate after the process exited. No remaining arm is selected or rejected based on its outcome, and no financial policy or parameter is changed. The new scientific service conservatively uses the existing full native audit after every action; its schema is not admitted to the engine's private incremental audit optimization. That financial guard remains unchanged.

The observed environment provides an eight-CPU quota, nine-CPU affinity and an 8 GiB memory limit. The serial process had approximately 200 MiB peak resident memory at inspection. These observations support testing a bounded process pool; they do not establish an actual speedup or a business/market capacity. Released replay detects its own resource allocation.

## Registered scheduling change

`scripts/replay_portfolio071_parallel.py` enumerates the identical 24 recipes in the identical registered order, calls the unchanged frozen `execute_trajectory` once for each new account, and preserves that order in the final campaign even when processes finish out of order. New processes use the `spawn` method, receive public source paths, manifest and recipe data, and never receive a live account, SQLite connection, signing key or writer lease. Each account has its own fresh directory and the existing recipe-derived contract identity. Replays in different output roots may repeat the same logical contract name; their account ownership and storage namespaces remain separate. No receipts or cash are pooled.

The default worker count is the lesser of four, available CPU quota/affinity, and a conservative memory bound. An explicit worker request must respect that observed bound. The resource calculation budgets at least 512 MiB per new worker plus a 512 MiB shared margin; it is a scheduling precaution, not an assurance against every possible memory limit. No worker cap is interpreted as a universal company or market scale limit.

Every new account performs all existing native financial checks and full audits. The scheduler records errors and partial artifacts without an automatic retry, selecting a replacement world, overwriting an account, or omitting a failed arm. Only a complete 24-arm result receives a new `campaign.json`. A separate orchestration receipt identifies the frozen financial source, scheduling source hash, this amendment, exact recipes, manifest, retained arms, new arms, resources and any failure.

Before scheduling, the runner verifies the original economic freeze document's exact hash, 24-arm denominator, 43,800-hour horizon, and all 72 recorded source files. The prospective orchestration freeze may amend exactly one of those files: `.github/workflows/portfolio071.yml`, with its original and replacement hashes explicitly bound. The remaining 71 files must be unchanged. Every staged native runtime file must retain its original hash; the workflow amendment cannot replace financial code. The runner also enforces all newly frozen orchestration source hashes and records both freeze-document hashes in the receipt. Pool construction, submission and retrieval failures retain every registered index as completed, failed or explicitly not started; they cannot silently drop accounts or trigger retries.

## Safe continuation of the canonical run

It must let the current account finish and close normally. The root records this gate outside the account namespace and removes only its own still-empty gate after the serial process has stopped. The scheduler refuses every existing incomplete account directory, including an empty gate.

With explicit `--resume-completed`, the scheduler checks each retained arm against its exact registered world, capital, policy, earned-only setting, identity, manifest and horizon. Both native ledger configurations and resource journals must contain the expected recipe-derived contract, opening equity, zero initial working reserve and manifest identity. The separate independent verifier replays both exported native tapes and checks the completed daily history, cash identities, pending tax commitments, immediate tax settlement, exact rolling profit, and the unchanged operating prefix before the account is retained. The remaining accounts start once with their own registered opening capital. No partial account is resumed.
