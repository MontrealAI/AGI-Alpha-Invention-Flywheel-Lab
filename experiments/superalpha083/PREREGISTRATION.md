# Super Alpha 083: rack-aware codec construction

Registered 2026-11-03 before implementation or codec outcomes. Base repository main: 215b22a5ed73b82ac1d909328d60157c48bd9958. Independent additive ownership: experiments/superalpha083 and one scoped workflow only. Existing owners, accounts and frozen experiments are unchanged.

## Opportunity selection
1. Passive joint static/dynamic friction: important actuator-free behavior, but independent transferable joint family calibration is not established. Source-informed hold, not a new physical experiment or defeat of the authors' results.
2. Autonomous original-requirement industrial planning: useful, but existing Operational075 already delivers exact original-client artifacts and has not established demand or complete-cost superiority. Repeating it is not a new opportunity.
3. Rack-aware exact erasure coding: selected narrow computational production test. Produce an executable encoder and recovery programs that recover actual bytes after registered failures; repair-read reduction could reduce storage/network burdens. No physical or market proxy is needed to establish byte correctness. Established LRC/RS systems are mandatory strong controls; a renamed known code is not invention.

## Frozen technical contract
Systematic k=8 source shards and n=14 equal-size stored shards, split among three racks of 5,5,4. Accept only a full-rank generator recovering every set of at most 3 erased shards, plus the complete loss of each rack. No corruption correction claim. Candidate is a binary XOR generator with six parity masks and a compiler for exact erasure repair. Nonzero codewords (255) provide an exhaustive distance check. All 469 nonempty <=3-symbol erasure sets and 3 racks are explicit checks. All methods may optimize placement and use identical original inputs, metadata, read budgets and acceptance.

Candidate construction: deterministic randomized local search, fixed seed 20261103, at most 24 independent starts x 400 proposals; 14-symbol placement is jointly mutable. Score first penalizes failures of the unchanged recovery contract, then worst single-loss helper count, then total helper count. This finite search budget is a registered comparison condition, not a mission timeout. Preserve failures, incumbents and counts. Prefer lower-complexity incumbent on ties. No after-outcome threshold change.

Controls: systematic GF(256) Reed-Solomon (Cauchy construction, 6 parity); conventional Azure-style (8 data,2 local,4 global) LRC construction with two 4-data local groups and Cauchy global rows, and an ordinary binary construction baseline. Names describe implementations, not vendor production certification. Exact finite rank checks must establish each control's recovery contract. Search placement for each with the same fixed prospective placement budget. Record strongest-current UniLRC and repair-efficient placement literature; if not reproduced, no universal/current-frontier superiority claim is permitted.

Repair metric: minimum number of distinct full stored shards read for exact linear single-erasure recovery; no subpacketization, piggybacking, compression, cache or partial-shard reads in this restricted metric. All helpers reside outside the lost shard. Count CPU, encode/repair latency, bytes, storage, network-read units, construction and verification separately. This is not an all-in market cost. Byte tests use fixed independent seeds 43001..43020 and shard lengths 1,17,1024; each accepted method must recover all registered erasure sets on each input. Fixed generated cases are developer-authored computational workloads, not customer requests or statistically independent market samples.

Fresh structural challenge: rack placements generated by seeds 92001..92020 after choosing the code, without retraining; all outcomes reported. This tests reconfiguration fragility, not new code-family generalization. Successor probe: reuse the linear code/repair compiler for GF(2) distributed matrix-vector evaluation with 8 row blocks, 16-byte rows and fresh seeded vectors, tolerating the same worker failures. Compare ordinary direct recomputation/coding; this is a different computational use but does not by itself establish causal discovery improvement, commercial demand or physical expansion.

## Costs and economic stopping rule
No real spending, outreach, private data, paid model/API/Platform access, accounts, keys, actuators, deployments or merged code. Reference capital $100,000 and full-year $3B complete-cost profit remain objectives, not achieved funds/profit. No native money is created for an unaccepted market. If full delivered rights, willing demand, prices, maintenance/security/support/financing/taxes and complete competitive cost evidence are missing, do not invent an annual sales trajectory or book profit. Report parametric break-even throughput only if clearly labeled and conservative. No annualizing short compute loops. A conditional technical win cannot establish the primary human-versus-frontier-agent lifecycle advantage without measured or explicitly grounded modeled full-workflow costs.

Pass as narrow implemented capability only when all byte/rank checks pass. Claim a tested repair advantage only relative to executable controls satisfying the identical contract, with unchanged storage and full disclosure of reliability differences. Claim no Super Alpha/new-industry/$3B admission without strong complete-alternative and market/cost evidence. Stop this finite experiment after the registered code, correctness, baseline and successor outcomes plus independent review; retain compact artifact and lesson regardless of sign.
