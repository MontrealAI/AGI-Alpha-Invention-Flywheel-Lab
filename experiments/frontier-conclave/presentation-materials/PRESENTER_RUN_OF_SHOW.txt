THE FRONTIER CONCLAVE Ω
Ω.001 · Can intelligence change the game, then test the new possibility?
PRESENTER RUN OF SHOW · 60 MINUTES

STATUS AND PROMISE
This is a synthetic, bounded experiment in constructing and testing a reusable instrument. It is not a financial product, a real customer transaction, autonomous negotiation, or proof of general invention. No successful live build or rehearsal is implied by these materials. Run the readiness checks below before promising a live demonstration.

THE QUESTION
“Three teams want the same useful tool. None can afford it alone. Is the project impossible, or are they trying to solve it the wrong way?”
The purpose is not to make elementary arithmetic look profound. It is to make the movement from a problem, to an explicit rule, to an executable instrument, to independent challenge visible.

THE WORLD · FICTIONAL WHOLE UNITS, NOT CURRENCY
A can contribute at most 120 units, B 160, C 220. Project cost is 420 and contingency 30. Required funding is 450, while combined caps are 500. A proposal of 90 / 140 / 220 meets the need. Sharing the funding changes the arrangement; it does not create money or prove that real teams would cooperate.
Every participant A, B and C must consent, including a zero-contributing participant. No zero-contribution exception is implied. Consent is an explicit synthetic input, not authenticated consent.

EXACT POLICY
All caps, contributions, project cost and contingency must be nonnegative whole numbers. Booleans, fractional numbers, strings and missing numeric inputs are invalid. Consent values must be actual booleans, not truthy strings or numbers. Invalid input must never be accepted.
For valid inputs, accept if and only if: every contribution is within its cap; every participant consents; and total contributions are at least project cost plus contingency. Excess contributions are permitted under this policy. The instrument does not allocate or refund the excess.
Show total contributions, required funding, nonnegative funding gap, nonnegative surplus, cap compliance, consent compliance, and acceptance. A rejected proposal is distinct from a claim that every possible proposal is impossible.

0–5 · THE REVELATION
Say: “Tonight we are not asking you to believe a claim about intelligence. We are asking you to inspect a small claim about what a constructed instrument can do.”
Show the world and ask for a private prediction: Can a proposal pass? What should cause rejection? Record predictions before revealing the sample allocation. Do not describe this familiar pooling arrangement as a newly discovered financial mechanism.

5–10 · CHANGE THE ARRANGEMENT
Reveal the pooled proposal: 90 + 140 + 220 = 450. Ask: “What would make this apparently valid proposal unacceptable?” Collect cap breach, refusal, insufficient funding and malformed inputs. Freeze the explicit policy. Changes after this point must be recorded as a new policy version with new expected outcomes.

10–23 · THE ATTEMPT
Show the specification and the build environment. State whether this is LIVE MODEL CONSTRUCTION, LOCAL PREPARED INSTRUMENT, or RECORDED REPLAY. Do not hide a mode change.
Use the latest capable frontier model actually available in the authorized ChatGPT Pro session, with computer use where supported. Verify its displayed identity and available capabilities before the session. Ask it to construct the checker from the frozen specification; use a visible manual copy/export handoff if direct HARNESS integration is not verified. Do not imply an API, account integration or unattended execution merely because the account is available. Start a visible timer; retain original specification, model identity, generated artifact and build evidence. Human edits count as interventions and must be disclosed.
Allow six minutes for the first build. Use the remaining time to inspect its rules and execute tests, not to retry indefinitely. A build that cannot complete is a valid observed failure.
If frontier-model access or the handoff is unavailable, say: “The model construction is not running here today. This prepared checker lets us investigate the policy and challenge process. It does not establish that a model constructed it live.”

13-MINUTE BUILD WINDOW · OPERATOR GATE
Do not execute arbitrary model-generated code or install a new runtime on stage. For the live checker, accept only a reviewed bounded arithmetic/boolean instrument. If using the HARNESS workshop, use its supported instrument format; do not assume that a ChatGPT response can be imported directly. Reject filesystem, network, imports or dynamic-code features. A general generated application requires separate review and testing before execution, not on-stage trust. Keep real personal information, credentials, customer data and payments out of every input and export.

23–35 · THE CHALLENGE
Run the frozen visible cases, then independently held-back cases if they were actually kept from the builder. Show expected and actual outputs side by side. An all-pass result supports these cases under this policy, not universal correctness.
Council choices: withdraw C consent; raise cost; exceed A cap while preserving total. Apply one change at a time and show the arithmetic. Restore the baseline between challenges.
If a failure occurs: retain the original failure, diagnose, allow one visible repair, rerun all regression cases, and label the repaired version. A case used for repair is no longer held out. Report both first-pass and repaired outcomes.
If there is no failure: do not manufacture one and call it a model mistake. An optional checker that tests only total funding may be shown as EXPLICIT FAULT INJECTION. Ask which challenge exposes its missing rule.

35–43 · THE RETURN
Export the instrument, specification, test evidence and policy version. Open the export in a fresh process or fresh session, without relying on the original in-memory state. Apply a new valid case, then a new rejection case. Keep this pair separate from the repair cases.
Fresh example: cost400/reserve30, contributions100/140/200 → ACCEPT; change B cap to139 → REJECT. This published example is a demonstration case, not held-out evidence.
If reopening fails, report export/reuse as failed. Do not substitute a successful earlier run without labeling it PREPARED REPLAY.

43–55 · WHAT DID WE ACTUALLY LEARN?
Ask: What changed the problem? Which rule prevented a misleading pass? What did the checker leave outside its world? What would have to be verified before anyone relied on it?
Say: “A spreadsheet can do this arithmetic. The useful question is whether a specified instrument can be constructed, inspected, challenged, repaired if necessary, and used again with an honest record of what happened.”
Distinguish construction quality from economic usefulness; tests from proof; a synthetic consent flag from actual agreement; a reusable artifact from evidence of improved general intelligence.

55–60 · THE NEXT FRONTIER
Summarize first-pass outcome, repairs/interventions, fresh-session reuse and limitations. Invite a next bounded investigation, rather than an unsupported commercial claim. No promise of profit, AGI, autonomous commerce or billion-dollar scaling follows from this session.
Close: “The frontier moves when a possibility becomes something we can inspect.”
